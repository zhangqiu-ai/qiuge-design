## 問題

介面只沿成功路徑驗一次，錯誤、不同角色與中途狀態可能被漏掉。修改完成後若沒有相同條件的比較，也難確認修正是否改壞其他部分。

## 做法

原作者 @emilkowalski 建議把 AI 用在幾種審查任務：刻意嘗試破壞已做好的功能，用狀態機檢查成功、錯誤及不同角色情境；完成後產生修改前後截圖，提出問題驗證想法，並製作介面變體供比較。原文也提到持續監控品質的循環，但未指定測試框架或驗收標準。

Kubai 於 2026-10-29 引用並認同，特別指出 Codex、Claude 可透過瀏覽器做自動互動測試。這是 Kubai 的使用觀點，不是原作者的工具評測，也不是可證明所有流程都被覆蓋的測試紀錄。本組來源是文字建議，沒有示範圖片或影片需要補入。

## 為什麼有效（推論）

收錄者推論：先列狀態再檢查，可降低只看正常畫面的遺漏；前後對照與變體則把修改變成可討論的證據。但截圖只能顯示部分結果，不能單獨證明行為正確，原帖亦無成功率數據。

## 借鑑要點

- **適合**：已有可執行介面，且成功、失敗與角色差異可明確列出的功能。
- **不適合**：沒有驗收條件，只要求 Agent 自行判定「已經夠好」。
- **移植時注意**：由人確認關鍵情境，把操作、預期結果與比較條件寫進可重跑測試；固定資料與視窗大小，將視覺對照作補充證據，另驗鍵盤、焦點及錯誤恢復。
